## What the user asked
Visitors want to know what they would actually use Jev for. Replace the one
generic answer from the regex `assessJevFit` with a page where someone pastes a
workflow and gets a specific decomposition — grounded in atlas records, evidence
status intact, and working with no model credentials configured at all.

## What changed
A new `/fit` page takes a pasted workflow (20–2,000 chars, three example chips)
and returns a verdict, a headline, 2–6 candidate decision points each badged
Choice / Score / Noul with its bounded options or scale and its opportunity
lens, keep-in-code vs keep-in-a-generative-model columns, a first experiment,
the related atlas records with their evidence status chips, and the caveats. The
whole result copies out as markdown.

Underneath, `runFitCheck` always runs the deterministic pass first
(`assessJevFit` + `searchKnowledge` over patterns/projects/opportunities, top 8)
and uses that as grounding for a model pass through the Vercel AI Gateway with a
zod-validated structured output. The model only ever decorates the deterministic
result:

- It is handed `{id,title,status,summary}` for the grounding records and told
  those ids are the only ones it may cite and that their status labels are not
  its to change. It is told it may not assert Jev's accuracy, speed, or cost,
  and that everything it writes is a hypothesis, not a finding.
- Post-validation drops any `relatedRecordIds` outside the grounding set and any
  `lens` outside `OPPORTUNITY_LENS_IDS`, strips `scale` off a Choice and
  `options` off a Score/Noul, trims overlong fields rather than discarding the
  answer, and always appends the deterministic caveats.
- **Every** failure returns `mode: "rules"` rather than an error: no gateway
  credentials, transport error, 12s timeout, a schema the model did not honour,
  or a model that produced no usable decision point. The primary model is tried,
  then the fallback, then rules.

The page renders a plain "rules-only result" note explaining why whenever that
happens, so the degraded answer is never passed off as the model one.

`POST /api/v1/fit-check` enforces the 20–2,000 bounds with 400s in the style of
`search.json`, sets `Cache-Control: no-store`, and applies a per-IP in-memory
limiter (5/min, 30/day) that **degrades to `mode:"rules"` rather than returning
an error**. The workflow text is never logged, echoed into an error, or stored —
the catch in `runFitCheck` is deliberately opaque for that reason.

The MCP `assess_jev_fit` tool now calls `runFitCheck` too, keeping its input
schema and its "not a benchmark" description caveat unchanged. **Per Jarvis's
review it passes `allowModel: false`**, so the public, unauthenticated MCP
endpoint can never spend gateway credit: it returns the deterministic pass plus
the grounded records, with the reason *"Served over MCP: deterministic grounding
only; the calling agent does the decomposition."* The caller is itself an LLM
and is better placed to do the decomposition from that grounding. The model pass
therefore runs only behind the website route, which is rate-limited per IP.

## Notes for Jarvis

**Env vars you must set (I never touched `.env*`):** these affect the `/fit`
page only — the MCP tool is deterministic and needs nothing. The gateway needs
either `AI_GATEWAY_API_KEY` **or** Vercel OIDC. `.env.local` currently has a
`VERCEL_OIDC_TOKEN` that the running server rejected, which is why the live
check fell back to rules — worth confirming the Vercel project has AI Gateway
access, or just setting `AI_GATEWAY_API_KEY` in Vercel for Production and
Preview. Nothing else is needed; the page is fully functional without either.

**Estimated cost per request:** measured, not guessed — system prompt 3,252
chars + user prompt 2,612 chars for a 257-char workflow ≈ **1,470 input tokens**,
rising to **~1,900** at the 2,000-char cap. Output is capped at
`maxOutputTokens: 1600` and typically lands well under that. Models are
`google/gemini-2.5-flash-lite` then `openai/gpt-5.6-luna`, both in the single
exported `FIT_CHECK_MODELS` array for swapping.

**One file beyond the brief's "may touch" list — please confirm:** I added
`src/lib/fit-check-result.ts`. The brief listed only `src/lib/fit-check.ts`, but
the production build failed hard (`Turbopack: the chunking context does not
support external modules (request: node:fs/promises)`) because the client
component importing `fit-check.ts` dragged the knowledge repository, and so
`node:fs`, into the browser bundle. The fix is the standard split: the
client-safe half (the result contract, the 20/2,000 bounds, and
`renderFitCheckMarkdown`) lives in the new file, `fit-check.ts` re-exports it so
every server caller keeps one import path, and only the browser component
imports the new module directly. It is a new file, not an edit to anyone else's.

**Shared files I edited, all minimal:**
- `src/components/app-navigation.tsx` — one entry added to `links`, after "Start here".
- `src/app/sitemap.ts` — `/fit` added to the `routes` array.
- `src/app/page.tsx` — one `<Link href="/fit">` in the existing hero CTA row,
  reusing `home-cta-secondary`. No layout rework.
- `src/mcp/server.ts` — the `assess_jev_fit` handler body only, plus its import.
  Tool name, input schema, annotations, and description are untouched, so

**`src/app/globals.css` was not touched at all** — the page uses Tailwind

One judgement call worth your eye: `runFitCheck` clamps its input at 7,000 chars
rather than the website's 2,000, because the MCP tool's own schema accepts 5,000
plus a stack list, and silently dropping 60% of an agent's workflow would be
worse than a slightly larger input. Since the review change that text now only
ever reaches the deterministic pass and the grounding search on the MCP path,
never a prompt. The website's 2,000 is enforced by the route, which rejects
rather than trims.
