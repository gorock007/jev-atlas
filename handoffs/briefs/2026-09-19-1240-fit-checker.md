# Fit checker: "Will Jev help my workflow?" page with a grounded model pass
agent: claude · model: opus · effort: high
prior work: handoffs/merged/2026-09-18-1708-homepage-builder-frame.md

## Why
Visitors ask "what would I use Jev for?". The existing `assessJevFit` in
`src/knowledge/repository.ts` is regex rules: it returns one generic decision
point. We want a page where someone pastes their workflow and gets a specific,
screenshot-worthy decomposition — grounded in atlas records, evidence status
intact.

## Decisions already made (do not reopen)
- Provider: **Vercel AI Gateway** through the `ai` package (already installed,
  v7 — read `node_modules/ai/docs` or its README/types before coding; do not
  trust memory of older AI SDK APIs). Use plain model strings. No provider SDKs,
  no API key in code. Auth is `AI_GATEWAY_API_KEY` or Vercel OIDC, both read by
  the SDK from env. Jarvis sets env vars; you never touch `.env*`.
- Model: `google/gemini-2.5-flash-lite`, fallback `openai/gpt-5.6-luna`. Put both
  in one exported constant so they are swappable.
- Structured output with a zod schema (zod 4 is installed). No free-form prose
  rendered from the model except short fields in the schema.
- **Graceful fallback is mandatory**: if the gateway is unconfigured, errors,
  times out (12s), or the rate limit trips, return the deterministic
  `assessJevFit` result with `mode: "rules"`. The page must work with no env set.

## Build
1. `src/lib/fit-check.ts` — `runFitCheck(workflow, records)`:
   - deterministic pass: `assessJevFit` + `searchKnowledge` (top 8 pattern /
     project / opportunity records) as grounding;
   - model pass: system prompt explains Choice / Score / Noul and the nine lenses
     (`src/knowledge/lenses.ts`), passes grounding records as
     `{id,title,status,summary}` only, and asks for:
     `verdict` (strong|promising|unclear|weak), `headline` (≤120 chars),
     `decisionPoints[]` (2–6: `step`, `primitive` Choice|Score|Noul, `question`,
     `options` or `scale`, `whyJev`, `lens` id), `keepInCode[]`, `keepInLlm[]`,
     `firstExperiment` (one paragraph), `relatedRecordIds[]`;
   - post-validate: drop any `relatedRecordIds` / `lens` not in the grounding set
     or `OPPORTUNITY_LENS_IDS`; always append the deterministic `caveats`.
   - The model must be told it may not assert Jev performance; status labels
     come only from records.
2. `src/app/api/v1/fit-check/route.ts` — POST `{workflow}`; 20–2000 chars, 400
   otherwise (follow the bounds style in `src/app/api/v1/search.json/route.ts`);
   per-IP in-memory limiter (5/min, 30/day) → falls back to `mode:"rules"`, not
   an error; `Cache-Control: no-store`. Never log the workflow text.
3. `src/app/fit/page.tsx` + `src/components/fit-checker.tsx` (client): textarea,
   three example chips (support triage, agent tool gating, content moderation),
   result view: verdict + headline, decision-point cards with primitive badge,
   keep-in-code / keep-in-LLM columns, first experiment, related records linked
   via `canonicalPathFor` with their evidence status shown, caveats, a
   "rules-only result" note when `mode:"rules"`, and `CopyContext`-style copy
   button for the result as markdown. Match the existing visual language
   (`src/app/start/page.tsx`, `record-chrome.tsx`); mobile 375px clean.
4. Wire-up: add "Fit check" to `src/components/app-navigation.tsx` (minimal),
   add `/fit` to `src/app/sitemap.ts`, and change the homepage hero's secondary
   area to include a link to `/fit` (one link in `src/app/page.tsx`, no layout
   rework). Make the MCP `assess_jev_fit` tool call `runFitCheck` too, keeping its
   input schema and description caveat.
5. Tests `test/fit-check.test.ts`: fallback when no env; schema post-validation
   drops unknown ids/lenses (inject a fake model fn — design `runFitCheck` to take
   an optional `generate` dependency); route bounds (400s); limiter falls back.
   No network in tests.
